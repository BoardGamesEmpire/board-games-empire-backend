# Elevated users do not read event chat

The Owner, Admins and Moderators together, the elevated users, read an event chat only as attendees of its event. Holding a server role gives no way into a chat: an elevated user who isn't an attendee is refused like anyone else, and one who is an attendee reads it as that attendee, under the same rules as the other attendees.

An event chat is the conversation of the people who came to an event, often friends in a living room. Everywhere else, an elevated user can read what the server holds: the Owner holds `manage:all`, and Admins and Moderators hold `read:public_content`, a read on every subject (`libs/database/src/lib/catalog/role-permission.catalog.ts`). A chat is the deliberate exception, for the privacy of friends' conversations and the project's priority that users control their own data (`AGENTS.md`). Without a record, a later review could "fix" the carve-out as an inconsistency. The decision was made when event chat was designed (#1532) and locked in #1543. This ADR is #1553.

- **One list names the types.** `ATTENDANCE_ONLY_RESOURCE_TYPES` (`libs/database/src/lib/catalog/attendance-only.ts`) lists the resource types that only attendance reaches, today `EventChatMessage`. `isAttendanceOnly` answers for a subject by name. Every guard below reads this list, so a type added to it, such as a chat reaction's (#1548), is covered at once.
- **The ability factory denies the types.** In `createForUser`, `denyAttendanceOnly` runs after the server-role pass and after the household pass, and before the event pass. CASL lets a later rule win, so an event role's grant, bound to the event attended (`{ eventId: '{{ eventId }}' }`), puts an attendee back in for that event and no other. No server role or household role can do it, whatever the Owner later edits into the permission catalog. Direct user permissions come last, and a denial among them still applies. `createForPlugin` and `createForApiKey` call `denyAttendanceOnly` after all their allows, so neither a plugin nor an API key reaches an event chat at all.
- **Direct allows are skipped.** `buildsDirectPermissionRule` (`libs/common/permissions/src/lib/api-key/holding-contexts.ts`) builds no rule for a direct permission that allows an attendance-only type, so no one can give a user one. A direct denial still builds. An API key can't be offered or hold such a permission either: `firstGrantableContext` in `libs/common/permissions/src/lib/api-key/grantable.ts` skips the type, so no key scope is offered that would never work.
- **The system actor keeps `manage:all`.** `createForSystem` never calls `denyAttendanceOnly`. Data jobs, such as the audit log's retention sweep, act as the system and work on every type.
- **The catalog gives chat to event roles only.** Five `event_chat_message` permissions (`read`, `create`, `update:own`, `delete:own`, and `delete` for any message) sit in `libs/database/src/lib/catalog/permission.catalog.ts`. Every event role holds the first four. The host, co-host and event moderator also hold `delete:event_chat_message`. Each carries a condition binding it to the event. Elevated roles hold no chat permission. `role-permission.catalog.spec.ts` guards this: no server or household role may hold a permission on an attendance-only type, and each such permission must bind `eventId`.
- **The access function is the second line.** `chatAccess` and `decideChatAccess` (`libs/api/event/src/lib/chat/chat-access.ts`) decide a read or a post from the user's own attendee row on a live event: that row's RSVP and event role, the event's chat settings and any host mute (`loadChatFacts`, `chat-facts.ts`). The decision reads no ability, so no grant satisfies it. It refuses every actor that isn't a user signed in as themself, a plugin acting for a user included, before it reads anything. An attendee a host removed is refused at once. Every chat route (#1545) and the chat's live topic (#1546) call it, so the two can't disagree.
- **No event read includes chat.** The ability's denial is a deny-all, and Prisma drops a deny-all nested in an `include` or `select` relation filter. The CASL extension on `DatabaseService` repairs only a top-level `where` (`docs/agents/gotchas.md`, "Deny-all conditions inside `include` / `select` are dropped"). So a read of an event that included its `chatMessages` would hand an elevated user the rows. `Event.chatMessages` exists in the schema for the cascade and for chat's own queries, and no event read names it. Chat is read only through the chat's own queries, after `chatAccess` admits the reader.

## What elevated users can still do

Without attending, nothing in a chat: not read, post, edit or delete. Moderating a chat is the hosts' job: a host, co-host or event moderator removes any message and mutes an attendee. An elevated user who needs to step in becomes an attendee the ordinary way, and then reads, and is moderated, like the others.

Their other grants stand. The Owner, an Admin and a Moderator can still delete an event: Admins and Moderators through `delete:event:moderate`, the Owner through `manage:all`. Deleting an event is a soft delete, and its chat closes with it: chat access reads only live events (`liveEventWhere`), so no one reaches the messages after the delete. The Owner can also cancel an event through `manage:all`. Admins and Moderators hold no server-role grant to cancel one.

## Considered options

- **Denial rows in the permission catalog.** They would show as data, which is their best argument. They can't be built: a catalog entry has no `inverted` field, so it can't express a denial. Were it added, the order of rules inside the server-role pass isn't fixed, so a denial row could lose to the wildcard it is meant to carve out. And a server role's catalog entries are meant to hold only what the User role lacks, not to mirror it (the comment at the top of `role-permission.catalog.ts`). Rejected.
- **The access function alone.** It decides everything a chat route and the live topic need, and it is simple. But any query scoped only by the ability, outside the function, would let an elevated user read through `read:public_content` or `manage:all`. The ability's denial closes that hole for every present and future reader of the type. Rejected as the only guard, kept as the second.

## Relation to #364, #365 and #419

#365 asks how wide a role-widened read should be, and recommends admin-scoped routes over reads that widen silently by role. #364 is the membership-scoped household list, its first instance. #419 is the elevated read surface, a route built only where a consumer exists, whose controllers still apply the ability. This ADR settles none of them. It fixes one answer inside their question: for an attendance-only type, the elevated read is no read, on every route, an elevated route included. An elevated route built under #419 must not offer event chat, and the denial would stop it if it tried. Whatever #365 decides for other lists leaves this unchanged.

## Still open

- **API keys and sockets (#1420).** API keys aren't accepted over WebSocket today, and a key can't hold a chat permission. If #1420 lets a key open a socket, whether and how a key may follow a chat is a new question, and this ADR's answer for keys stands until it is decided.
- **Hiding a person (#1586).** Whether an attendee may hide one person's messages for themselves, and what a block between two attendees means in a shared chat. Neither is part of the first version, and neither changes who counts as an attendee.

## Consequences

- An elevated user can't read a chat to look into a report of abuse in it. The people who can are its attendees and its hosts. If a server ever needs a read path for its elevated users, that is a new decision that supersedes this one.
- The protection is the server's rules, not secrecy from whoever runs the database. Messages are stored as plain rows, and the operator who controls the database can read them there, a deleted event's messages included, which stay in the database as rows. The decision stops the server's roles, not the operator's own access to their data.
- Any new type that belongs only to attendees must join `ATTENDANCE_ONLY_RESOURCE_TYPES`, hold its permissions on event roles only, and be read through no relation `include` or `select`.
- An elevated user who attends an event reads its chat under the event's settings, as any attendee does. One attending as a spectator reads, and posts only where the event allows spectators to, under the same RSVP settings as the other attendees.
- The Moderator entry in `GLOSSARY.md` says a Moderator can read everything except event chats it does not attend.
