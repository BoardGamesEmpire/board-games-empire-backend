# Retried writes use client request ids

A client that loses the response to a write sends it again. It can't tell a write that failed from one whose answer went missing, and the client queues writes offline, so a second attempt is ordinary rather than rare. Each write a retry can break gets one of three answers (#252):

- **A create the client may send again takes a client request id.** The `clientRequestId` field in the body is stored on the record, under a unique scoped to the user who created it. The create goes through `createOrReplay` in `@bge/database`. It looks up the record under that user and key first, and runs the create only if there is none. If the create then trips the unique, a concurrent duplicate committed first, and a second lookup finds its record. Either way, the answer to the retry is a replay: the original record, with the same 2xx response, whatever the retry's payload says. The lookup ignores soft delete, so a record deleted since is still the create's outcome. `POST /households`, `POST /feedback/reports` and `POST /events` work this way.
- **A state change already at its target answers 2xx.** When a record is already in the state the request asks for, and the caller is the one entitled to have put it there, the answer is 2xx with the current record, and nothing is emitted. A record in some other state keeps its current error. The routes, and the work to make them answer this way, are in #901.
- **A create with a natural key uses it.** Game import is to build its jobs' keys from the request's `correlationId` (#900), so it needs no second key.

## Considered options

- **An `Idempotency-Key` request header.** One mechanism for every verb, which is its best argument. Its cost is fingerprinting each request, capturing each response, handling a retry that arrives while the first attempt is still running, and deciding how long to keep it all. Nothing needs that today: every write a retry can break is a create, which a client request id fixes, or a state change, which the 2xx answer fixes. It is deferred, not rejected (#905). The condition for revisiting it is a write that neither answer can make safe. The field name `idempotencyKey` stays unused on the wire, so the header can have it.
- **Catching the unique violation first, and looking up only then.** Household create and feedback submit both used to work this way. Its best argument is one fewer query per keyed create, but that query is an indexed point read. Rejected because catching first lets a check that has changed since the original refuse the retry of a create that succeeded. A household deleted since, or an invitee who has blocked the creator, turns that retry into a 403 or a 404, which no client can tell from a real refusal.
- **Leaving a repeated state change's error for clients to interpret.** Clients would read the error codes (#822) and treat some as "already done". It needs no server work. Rejected because every client would need its own list, per route, of which errors mean success, and a retried ownership transfer answers 403, which no code can make harmless.

## Consequences

- Every new create a client may queue takes a `clientRequestId`, through `createOrReplay` and the shared `ClientRequestIdProperty` validation. Its update DTO must omit the key: a PATCH that rewrote it would strand the queued retry into a second record (#534).
- What a replay re-runs is decided per record type, from the `replayed` flag the helper returns. A replay re-runs what is safe and heals: household and event create evict cached permissions again. It skips what would be noticed twice, so event create doesn't notify its invitees again and feedback submit doesn't forward the report to its sinks again.
- A replay returns the record itself as it stands, but what it embeds from other users is read as the caller may read it now. Event create's dates, attendees and policy each come under their own read ceiling, as `GET /events/:id` serves them, so a creator who has lost read on the event since doesn't get its roster from a retry.
- A key is no way around the route's own permission check, which runs before the lookup: a user banned from a kind of create is refused its retry too.
- The routes still open are #899 (media, games and webhook subscriptions take a key), #902 (an event's dates and nominations, once a client queues them) and #903 (writes that change nothing but still notify).
